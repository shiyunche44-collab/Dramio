# /step：完成一个步骤

指定的步骤（可能为空）：$ARGUMENTS

一次只完成**一个**步骤。严格遵守 `docs/progress.md` 中的“自主推进设置”；设置没有授权的事项，一律先问用户。

## 0. 同步主线

```bash
git fetch origin main
```

- 会话分支没有自己的提交时：`git checkout -B <当前会话分支> origin/main`（远端还没有 main 时跳过）。
- 会话分支有未合并的提交时：先看它属于哪个步骤的 PR。按 [ship.md](ship.md) 处理完这个 PR，再继续。
- 用 GitHub MCP 列出本仓库打开的 PR。发现未合并的步骤 PR，同样按 ship.md 处理。

## 1. 选择步骤

1. `$ARGUMENTS` 指定了步骤时，就做这个步骤（前提是依赖都已 ✅；否则说明原因并停下）。
2. 否则，有 🔄 的步骤时，从 progress.md“子任务”中第一个未勾选的项续做。
3. 否则，选当前里程碑内编号最小、依赖全部 ✅ 的 ⬜ 步骤（`python3 tools/workflow/hooks.py summary` 会给出“下一个可开始的步骤”）。

检查阻塞：

- 该步骤相关的待决事项是否还是“待决”；
- 需要的环境变量是否存在（`printenv 变量名 >/dev/null`，**不要打印密钥的值**）；
- 需要访问的供应商域名是否可达。

被阻塞时，换做当前里程碑内另一个不受阻塞的步骤（同时进行中的步骤不超过 2 个），并在交接日志中说明原因。没有可做的步骤时，按“必须停下”处理。

## 2. 探索与计划

使用 `step-planner` 子代理（Agent 工具，`subagent_type: step-planner`），把步骤编号和 roadmap 中的那一行交给它。它会返回步骤卡和子任务清单。

检查计划：范围是否与 roadmap 中该步骤的交付和验收一致；“不做”是否写清楚；估时是否合理。然后：

1. 写入 progress.md：“步骤卡”“子任务”两节；“当前步骤”改为该编号；“步骤状态”改为“进行中”；“工作分支”改为会话分支；“本步费用”的已花费清零；
2. roadmap 中该步骤标为 🔄；
3. 运行 `make arch-check`，然后提交（`P0-01：开工，写入步骤卡`）并推送。**先存档再写代码。**

## 3. 实现

- 用 Claude Code 的任务列表跟踪子任务。
- 每完成一个子任务：在 progress.md 中勾选 → 提交 → 推送。这是检查点，容器随时可能被回收。
- 只做步骤卡中“做”的部分；遇到“不做”范围内的事，记入交接日志作为后续事项。
- 代码必须满足 CLAUDE.md 中的全部不变量。P0 验证代码放在 `spikes/`，DramaIR 放在 `packages/drama-ir/`。

**费用控制**：

- 调用付费 API 前，先按“调用次数 × 单价”估算；单价不明时先调用 1 次，实测后再外推；
- 每次调用后更新 progress.md 的“已花费”；
- 本步已花费加上预计费用将超过上限时，停止调用，登记待决事项（说明还需要多少钱、用来做什么、不做的替代方案），然后按“必须停下”处理。

## 4. 验证

使用 `verifier` 子代理，把步骤卡中的验收标准交给它。它会在全新的上下文中逐条运行检查，返回“通过 / 失败 + 证据”。

- 有失败项：修复后重新验证。同一问题修复 3 轮仍未通过时，按“必须停下”处理。
- 需要主观判断的验收项（例如选定妆、人工评分、选供应商）：准备好候选和推荐，在 progress.md 的“待决事项”表中登记，编号取 `D-001` 起的下一个，状态为“待决”。候选的产物路径写在“候选”列中。该步骤保持 🔄，转去做其他步骤。**不要替用户做主观决定。**

## 5. 评审

使用 `arch-reviewer` 子代理审查本步骤的改动（`git diff origin/main...HEAD`）。修复所有阻断项；建议项可以修复，也可以记入交接日志。

## 6. 交付

按 [ship.md](ship.md) 执行：标记完成并移动进度指针 → 提交推送 → 创建 PR → 等待 CI → 合并或停下。

## 必须停下的情形

出现以下情况时，先把状态存档（progress.md 写清楚“需要用户做什么”，然后提交并推送），再向用户汇报：

| 情形 | 告诉用户什么 |
|---|---|
| 缺少密钥 | 需要的环境变量名；在云环境设置（会话标题栏的环境菜单 → 编辑）中添加环境变量，新会话才会生效。**绝不要求用户把密钥贴到聊天里** |
| 域名被网络策略拦截 | 具体域名；在云环境设置的网络访问中放行 |
| 等待用户决定，且里程碑内没有其他可做的步骤 | 待决事项的编号、候选、推荐 |
| 将超出费用上限 | 还需要多少钱、用途、替代方案 |
| 范围膨胀：超过估时 2 倍、需要新 ADR、需要修改检查规则或添加豁免 | 拆分方案，或者需要的 ADR / 豁免申请 |
| 同一问题修复 3 轮仍失败 | 失败现象、已尝试的办法、建议 |
| PR 涉及受保护路径 | PR 链接，请用户审阅合并 |

## 禁止事项

- 没有验证证据就把步骤标为 ✅；
- 修改 `tools/archcheck/rules.toml`、`exceptions.toml` 来让检查通过；
- 直接推送 `main`，或强制推送；
- 自行把待决事项改为“已决”（只有用户能决定）；
- 顺手开始下一个步骤的工作（下一个步骤由 /continue 决定）。
