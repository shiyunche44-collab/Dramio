# ADR-0011：模型网关的实现语言

- **状态**：Proposed
- **日期**：2026-10-13
- **决策人**：@shiyunche44-collab
- **关联**：架构文档 §7、§14、§15；不变量 INV-01、INV-05、INV-07；ADR-0004（模型网关）、ADR-0008（语言分工，把网关语言留给本 ADR）

## 背景

ADR-0008 规定模型网关用“TypeScript 或 Go，在 P1 启动时通过新 ADR 确定”。P1-08 要做网关 v0：独立服务、`audio.tts` 一种能力、一家供应商、静态路由、幂等键、成本账本。

P0 的经验（`spikes/poc`，全部用 Python 直连供应商）：

- 供应商差异大：Ark 有 Agent Plan（`/api/plan/v3`）与按量两套端点和计费口径；账号级 429（MiniMax `2056`、Ark `AccountQuotaExceeded`）需要“不重试、降级”；视频任务是提交 + 轮询 + 下载三步；错误的计费口径各不相同（网络错误是否计费要保守估计）。
- 网关的工作基本是 I/O 与状态：HTTP 适配、重试与限流、幂等键查表、账本写入、路由。没有重计算。
- 调用方是 Python Worker（媒体与模型处理）和 TypeScript（API、Workflow）；两边都只经 HTTP/gRPC 访问网关（INV-01、INV-03）。
- P0 的 Python 适配器是验证代码，不是产品代码（`spikes/` 在 P1-30 清空，任何产品代码都不能依赖它）。

## 决策

**倾向：TypeScript。** 本 ADR 的最终选择由决策人确认（待决事项 D-021）。

- 网关用 TypeScript 实现，与 `apps/api`、`services/orchestrator` 共用工具链和共享包（`@dramio/*`，包括幂等键、账本记录、错误分类的类型）。
- 供应商适配器按 P0 的实测行为重新实现，不移植 `spikes/poc` 的代码；契约（请求 / 响应 / 错误分类 / 计费口径字段）写成 JSON Schema，生成 TS 与 Python 类型。
- 账号级额度错误、审核拒绝、瞬时错误分三类处理（不重试 / 不重试 / 重试），计费口径（`reported` / `estimate` / `free`）作为账本字段（P0 的 `calls.jsonl` 已验证）。

## 备选方案

| 方案 | 优点 | 缺点 | 不选的原因 |
|---|---|---|---|
| TypeScript（倾向） | 只有两套工具链；与 API / 编排共享类型和包；I/O 密集场景足够；团队前端栈一致 | CPU 密集和大流量下性能不如 Go；Node 对长连接 / 流式需要谨慎 | — |
| Go | 并发与资源占用好；单二进制部署；适合高吞吐代理 | 引入第三种语言（ADR-0008 的“TS 或 Go”允许，但多一套工具链与招聘成本）；类型共享要靠生成 | P1 的网关吞吐低（单集几十到几百次调用），性能收益用不上 |
| Python | P0 的适配器经验可直接参考；与 Worker 同语言 | 需要先修改 ADR-0008（它限定网关为 TS 或 Go）；会让 Worker 与网关边界变模糊，容易被绕过（INV-01）；Web 服务栈要另选 | 与既有语言分工冲突，且 spikes 代码本来就要删除，复用收益有限 |

## 后果

- 正面：两套工具链；网关契约和 TS 侧类型天然一致；适配器按真实行为重写，避免把验证代码带进产品。
- 负面 / 代价：P0 的 Python 适配经验要重新实现一遍（预计每个适配器几百行，行为已被 P0 报告记录）；若后续吞吐成为瓶颈，需要按 §8 的触发条件重新评估。
- 约束：网关之外不 import 供应商 SDK、不硬编码模型 ID（INV-01）；网关负责幂等键与计量（INV-05、INV-07）。选 TypeScript 时 `architecture.md` §14 技术栈表中“模型网关”一行的“Go 或 TypeScript”随本 ADR 转 Accepted 同步改为 TypeScript。

## 复审条件

网关出现 CPU 瓶颈（单实例 CPU 持续 > 70% 且主要耗在序列化 / 加解密）；或同一能力接入 3 家以上供应商后适配器数量使 TypeScript 类型维护成本明显上升；或视频类长任务的并发轮询在 Node 下出现可观测的事件循环延迟。
