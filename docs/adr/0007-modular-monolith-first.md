# ADR-0007：先模块化单体，按触发条件再拆分服务

- **状态**：Proposed
- **日期**：2026-09-30
- **决策人**：@shiyunche44-collab
- **关联**：架构文档 §3.2、§3.3；docs/governance.md §8；不变量 INV-03

## 背景

项目初期团队规模小、领域边界还在摸索。过早拆微服务会带来分布式事务、部署编排、跨服务调试等成本；但完全不设边界的单体，后期又拆不开。

## 决策

- 业务 API（`apps/api`）先做成**模块化单体**：按领域（项目、剧本、资产、分镜、审核、发布、计费）划分模块，模块之间只通过公开接口调用，不跨模块直接访问数据表。
- 模型网关、编排（Temporal Worker）、GPU Worker 从一开始就是独立部署单元，因为它们的伸缩特性与业务 API 完全不同。
- 拆分某个模块为独立服务，必须满足 docs/governance.md §8 中的触发条件，并写 ADR。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 一开始就拆微服务 | 团队小，运维与协作成本过高 |
| 不设模块边界的单体 | 后期无法拆分，耦合随时间恶化 |

## 后果

- 正面：初期开发快；边界清晰，将来按需拆分。
- 负面：需要靠检查工具和评审守住模块边界（单体内边界更容易被破坏）。
- 约束：P1 引入 dependency-cruiser（TS）/ import-linter（Python）检查模块内部边界（governance §5.2）。

## 复审条件

满足 governance §8 中任一拆分触发条件。
