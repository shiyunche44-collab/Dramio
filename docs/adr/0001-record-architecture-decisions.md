# ADR-0001：用 ADR 记录架构决策

- **状态**：Proposed
- **日期**：2026-09-30
- **决策人**：@shiyunche44-collab
- **关联**：docs/governance.md §4

## 背景

Dramio 是长期演进的项目：模型能力按月迭代，团队成员会变化，AI 编码助手也会参与开发。如果架构决策只存在于会议和聊天记录里，半年后没人记得“为什么这样设计”，代码就会在需求压力下逐步偏离架构。

## 决策

- 所有架构级决策都以 ADR（Architecture Decision Record）的形式记录在 `docs/adr/`，与代码一起评审、一起版本管理。
- 必须写 ADR 的情形见 docs/governance.md §4.1。
- ADR 一旦 Accepted 就不再修改正文；决策变化时写新的 ADR，并把旧 ADR 标记为 Superseded。
- 格式和索引由 `tools/archcheck` 在 CI 中自动校验。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 只维护一份大架构文档 | 只能看到“现在是什么”，看不到“为什么”和“曾经放弃了什么” |
| 放在 Wiki / 飞书文档 | 与代码脱节，无法在 PR 中一起评审，也无法自动校验 |

## 后果

- 正面：决策可追溯；新成员和 AI 助手能读懂设计意图；“偏离架构”变成显式的 ADR 变更，而不是悄悄发生。
- 负面：每个重大决策多花 30–60 分钟写文档。
- 约束：架构文档（docs/architecture.md）描述当前状态，ADR 记录决策历史，二者在同一个 PR 中同步更新。

## 复审条件

ADR 数量增长到难以检索（例如超过 100 篇）时，考虑按领域分目录或引入检索工具。
