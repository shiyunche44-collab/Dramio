# ADR-0012：DramaIR v1 的范围

- **状态**：Proposed
- **日期**：2026-10-13
- **决策人**：@shiyunche44-collab
- **关联**：架构文档 §4；不变量 INV-02；ADR-0002（DramaIR 作为唯一事实来源）；P1-03；`docs/reports/p0/P0-14/dramair-v0-revision-proposal.md`；TD-001

## 背景

DramaIR v0 是为 P0 验证写的草案 Schema，贯穿了 P0-03 ~ P0-13。主版本升级需要先写 ADR（governance §4.1）。P0 的实测给出了 v0 的缺口（提案清单见上面的报告）：地点没有实体、台词只能挂在镜头上、`kind` 混合了台词类型与口型需求、音色是自由文本、镜头时长与配音时长不闭环（P0-13：63 个镜头中 28 个台词超出，10 个超出 > 0.3 秒）。

## 决策

DramaIR v1（P1-03）包含以下变更，其余按“后果”处理：

1. **Location 实体**：镜头通过 `location_id` 引用，场的 `setting` 保留为默认值。
2. **台词可先挂在场上**：支持“已分场、未分镜”的中间状态；分镜后台词挂到镜头，场上不再保留（保证守恒）。
3. **口型需求移到镜头级**：`generation_policy.lip_sync`（`required` / `none` / `native`），台词 `kind` 只保留 `dialogue` / `voiceover`。
4. **音色绑定**：`characters[].voice` 改为 `{description, voice_id?}`；音色库实体由 P1 另议。
5. **`duration.resolved_s`**：音频先行后回填的实际时长；`hint_s` 保留为分镜意图。
6. **Look 实体与 `look_id`**（定妆 / 服装变体，随 Location 一起）。P0 里没有单独证据，依据是定妆（P0-06）已按角色外观 + 服装生成，P1-12 的候选打分需要一个稳定的外观引用——属于前瞻性设计。
7. **为增量重算与锁定预留**：`locks`、Take 的命名空间在 v1 保留但不实现（P2 上线）。这是**前瞻性预留**，没有 P0 消费者；若评审认为违背“没有消费者就不进 v1”，可移出。
8. 情绪枚举扩展 `suspicious`、`determined`（证据较弱：来自 P0-03 模型自发使用；提案表归为 v0.x，这里合并进 v1 是因为 v1 本来就是破坏性升级，没有单独发 v0.x 的必要）。

**工程约束（不是 Schema 变更）**：v1 起 Schema 向后兼容检查与生成类型（zod、pydantic）进 CI（P1-03），手写校验器退役（TD-001 偿还）。

**不进 v1**：`order`、`beat`、`lens_mm`、`position`、Bible、Prop（没有消费者，等需求出现再写 ADR）。node_key 与缓存元数据不进 IR，由编排与网关层持有。

迁移与兼容策略：v1 是破坏性主版本升级；提供 v0 → v1 迁移脚本和迁移说明（REVIEW.md 对破坏性变更的要求），v0 数据在迁移脚本维护期内仍可读；冻结样例 `ep01.json` 保持 v0 不变并补一份 v1 版本。

## 备选方案

| 方案 | 优点 | 缺点 | 不选的原因 |
|---|---|---|---|
| 在 v0 上继续加可选字段（0.x） | 不破坏兼容 | v0 所有字段必填、`additionalProperties: false`，且 #2、#3 是语义变更，无法兼容地表达；没有兼容性 CI，越改越难审 | 语义变更需要主版本 |
| 把 architecture §4.2 的完整模型一次做完 | 一步到位 | 许多实体 P1 没有消费者（Bible、Prop、`beat`、`lens_mm`） | 过度设计，违背“先有消费者” |
| 本 ADR 的范围（按 P0 证据挑选） | 1–5 项有 P0 的数据和消费者；6–8 项已在上面标明证据强度 | 以后仍会有 v2 | 采用 |

## 后果

- 正面：P1-12 / P1-13 / P1-14（候选打分、音频先行、视频）需要的字段都在 v1；一致性问题（Location、Look）有落点。
- 负面 / 代价：所有 P0 spikes 代码和 LLM Prompt 不跟进，P1 重写（符合“spikes 不被依赖”）；v0 → v1 迁移脚本要维护到不再有 v0 数据。
- 约束：v1 Schema 变更必须通过兼容性 CI；生成类型不能手改（INV-02）。

## 复审条件

P1-03 实现中发现某一项没有消费者或与 P1 的实现冲突；或 P1-28 试产暴露了 v1 表达不了的制作需求。
