# ADR-0002：DramaIR 作为全链路唯一事实来源

- **状态**：Proposed
- **日期**：2026-09-30
- **决策人**：@shiyunche44-collab
- **关联**：架构文档 §4；不变量 INV-02

## 背景

剧本、分镜、配音、画面、剪辑各环节都需要读取“这一镜拍什么、谁说什么、多长时间”。如果每个模块各自定义一套数据结构，就会出现多份互相不一致的“剧本”，自动化和增量重算都无从谈起。

## 决策

- 用 JSON Schema 定义 DramaIR（剧 → 集 → 场 → 镜 → 台词，以及设定集、角色、场景等），放在 `packages/drama-ir/`。
- TypeScript（zod）与 Python（pydantic）类型**只能由 Schema 生成**，不允许手写同义结构。
- 所有模块读写剧本数据都通过 DramaIR；需要新字段时修改 Schema，而不是在模块内另起结构。
- Schema 采用语义化版本：
  - 新增可选字段 → minor；
  - 删除字段、改类型、改语义 → major，必须附带数据迁移脚本和新的 ADR。
- 每次保存 DramaIR 生成不可变修订版本（revision），用 JSON Patch 记录差异。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 自由文本剧本 + 各环节自行解析 | 解析不稳定，无法精确判断修改影响范围 |
| 直接用数据库表结构作为模型 | 前端、Worker、LLM 结构化输出都需要同一份定义，表结构不适合作为跨语言契约 |

## 后果

- 正面：一份定义贯穿前端、API、工作流、Worker 和 LLM 输出；增量重算可以精确到字段。
- 负面：Schema 演进需要纪律；major 版本升级有迁移成本。
- 约束：P1 起 CI 增加“生成类型与 Schema 一致”和“Schema 向后兼容”两项检查（governance §5.2）。

## 复审条件

出现某个环节确实无法用 DramaIR 表达、且扩展 Schema 代价过高的情况。
